DESIGN EXPLORATION · ПОРТАЛ ИЦ

Пять моделей рабочего реестра

Все концепции используют один дизайн-язык из `design/`: content-first surfaces, таблицы без вертикальной сетки, 40/32 px controls, 30 px statuses, progressive disclosure и ограниченную семантическую палитру. Различается не оформление, а модель работы.

Статус источников. В `design/` не обнаружены отдельные документы Visual Design Audit и Migration Strategy. Ниже audit трактуется как проверка наблюдаемых проблем текущего реестра, а migration — как оценка сложности перехода без изменения backend/API.

Рейтинг при выбранных приоритетах

Что объединять, а что не смешивать

  • Основа 01: collection surface, tabs, search, компактная process strip.
  • Из 03: optional inspector только как desktop enhancement и только на данных list payload.
  • Из 05: последний комментарий как quieter secondary signal в строке.
  • Из 04: advanced filters в drawer, а не постоянной панели до появления backend-контракта.
  • Не объединять lanes из 02 с постоянным inspector из 03: таблица перестанет быть главным объектом.
  • Не переносить постоянную filter rail из 04 без сохранённых представлений.
  • Не показывать искусственную event chronology из 05: list API не гарантирует последнее процессное событие.
  • Не вводить drag-and-drop между статусами: это изменит workflow и ACL.
  1. Сначала shell, toolbar, tabs и table primitives без изменения данных.
  2. Затем локальная process strip на доступных counts или статических entry points.
  3. После отдельного API-контракта — attention counts, saved filters и full inspector.
  4. Карточка заявки и администрация остаются вне этой миграции.

Рекомендация для обсуждения

Базовое направление: 01 + строго ограниченные элементы 03 и 05

Это не автоматический выбор. Концепция 01 лучше всего соответствует collection-page паттерну SVG-архива и текущему API. Из 03 стоит взять только локальный preview на уже загруженных данных; из 05 — визуальную роль последнего комментария. Концепция 02 сильнее для руководителей, а 04 станет перспективнее после появления сохранённых фильтров.

Перед production-реализацией нужно выбрать базовую концепцию и допустимые заимствования. Без этого разные модели взаимодействия нельзя безопасно смешивать.
