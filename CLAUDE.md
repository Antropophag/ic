# Инструкции для Claude Code

## Рабочий язык

- Общение с пользователем, планы, документация, issues, pull request и ответы
  на review ведутся на русском языке.
- Имена классов, методов, переменных, API-полей и другие технические
  идентификаторы остаются на английском.

## Контекст проекта

Перед изменениями прочитайте относящиеся к задаче документы:

- `README.md` — запуск и структура;
- `docs/product-spec.md` — согласованное поведение;
- `docs/business-rules.md` — стабильные идентификаторы правил;
- `docs/architecture.md` и `docs/data-model.md` — архитектура и схема БД;
- `docs/engineering-standards.md` — Definition of Done;
- `docs/test-strategy.md` — тестовые контуры и пороги покрытия;
- `docs/roadmap.md` — порядок дальнейших работ;
- `docs/ai-review.md` — политика AI-review.

Изменение поведения считается неполным без обновления соответствующей
документации и пользовательской инструкции.

## Работа с Git

- Не выполняйте прямой push в `main`; каждое изменение проходит отдельный PR.
- Перед началом работы обновите `main` и создайте тематическую ветку.
- Сохраняйте пользовательские изменения и не применяйте destructive Git-команды.
- Заголовок, описание и комментарии PR пишите на русском языке.
- Связывайте PR с issue через `Closes #<номер>`.
- Назначайте ровно одну метку `type:*`, одну или несколько `area:*` и ровно одну
  `risk:*`. Workflow, ACL, миграции и безопасность всегда имеют `risk:high`.

## Независимый Codex review

- После реализации и проверок запустите read-only `$pr-review` относительно
  `main`. Findings исправляются только в отдельном implementation-проходе.
- Codex review дополняет deterministic CI, Qodo, CodeRabbit и человеческий
  review, но не заменяет их.

## Qodo и merge

- Никогда не вызывайте Qodo вручную командой `/agentic_review`: приложение
  запускает проверку автоматически, а ручной вызов может перезапустить review.
- `PR Summary` и сообщение о выполняющейся проверке не являются итогом.
- Перед merge проверьте, что итоговый комментарий `Code Review by Qodo` относится
  к текущему head commit, все review threads закрыты и обязательный CI зелёный.
  Каждое замечание должно быть исправлено либо аргументированно отклонено как
  ложное; Qodo остаётся рекомендательным и не заменяет человеческий review.
  Это касается review threads и от Qodo, и от человека — merge в `main`
  запрещён, пока остаётся хотя бы один незакрытый.
- На каждое исправленное замечание ответьте по-русски со ссылкой на commit и
  закройте discussion. После push ожидайте автоматическую перепроверку.
- Не сливайте PR без явного разрешения пользователя.

## Проверки

Основной локальный gate:

```bash
make check
```

Для изменений API, БД и workflow дополнительно поднимите реальный контур:

```bash
make e2e
```

Порог backend Domain/Application — не менее 90% statements. Для frontend
statements, branches, functions и lines — не менее 80%. Процент не заменяет
позитивные, негативные, ролевые и конкурентные сценарии бизнес-правила.

## Инварианты реализации

- Проверяйте авторизацию для каждого действия на сервере; UI capability не
  является средством защиты.
- Процессные операции выполняйте транзакционно и используйте optimistic locking.
- После `SELECT ... FOR UPDATE` повторно проверяйте статус, роль и актуальную
  `lockVersion`; конкурентная запись должна завершаться контролируемым конфликтом.
- Любой асинхронный frontend-запрос защищайте от позднего ответа. При закрытии или
  переключении карточки инвалидируйте запрос, а после конфликта отключайте все
  действия, зависящие от устаревшей версии.
- Для исправления гонки добавляйте регрессионный тест с обратным порядком ответов
  или закрытием экрана во время запроса.
- Входные JSON-значения проверяйте по типу до нормализации; не приводите массивы и
  объекты к строке.
- Документы хранятся вне web root и проверяются по размеру, MIME, расширению и,
  где требуется, внутренней структуре.

## Секреты и внешние системы

- Никогда не показывайте, не логируйте и не коммитьте содержимое `.env`, webhook
  Bitrix24, LDAP credentials и другие секреты.
- Допустимо использовать уже настроенные локальные секреты только для относящейся
  к задаче операции.
- Тесты используют синтетические данные и не обращаются к production LDAP, SMTP,
  Bitrix24 или корпоративному файловому хранилищу.
- Учитывайте корпоративный TLS/антивирус: демонстрационный комплект должен
  разворачиваться без Composer и npm на целевой машине.

## Локальные рабочие деревья

В проекте могут существовать параллельные Git worktree. Перед редактированием
проверьте текущую ветку и `git status`. Файл `.env` игнорируется; при необходимости
используйте локальную ссылку на основной `.env`, но никогда не добавляйте её в Git.
