Проведи декомпозицию frontend текущего проекта.

Работай непосредственно с исходным кодом репозитория. Основная цель — уменьшить сложность `frontend/src/App.vue`, сохранив существующее поведение приложения.

## Главная цель

Разделить большой `App.vue` на несколько естественных экранов и крупных компонентов так, чтобы:

* разработчику не приходилось открывать один файл на 1600+ строк;
* логика конкретного экрана находилась рядом с его шаблоном;
* связанное состояние не было размазано между большим количеством файлов;
* количество новых абстракций оставалось минимальным;
* функциональность, API-контракты и внешний вид не изменились.

Это рефакторинг, а не разработка нового интерфейса.

## Важные ограничения

Не внедряй в рамках этой задачи:

* TypeScript;
* Pinia;
* Vuex;
* Feature-Sliced Design;
* структуру `shared/entities/features/widgets`;
* Vue Router;
* новый UI-kit;
* новую библиотеку управления запросами;
* глобальный event bus;
* provide/inject как замену нормальным props и events;
* отдельный composable для каждой маленькой операции;
* отдельный компонент для каждой кнопки или модального окна;
* изменение backend API;
* изменение формата запросов и ответов;
* изменение дизайна;
* масштабное переписывание CSS;
* новые архитектурные слои «на будущее».

Не делай механическую декомпозицию, при которой один большой файл превращается в десятки маленьких файлов с постоянной передачей большого числа props и events.

## Предварительный анализ

Перед изменением кода изучи:

* `frontend/src/App.vue`;
* `frontend/src/api.js` и другие API-модули;
* `frontend/src/registry.js`;
* `frontend/src/requestDeepLink.js`;
* `frontend/src/main.js`;
* существующие frontend unit-тесты;
* Playwright/E2E-тесты;
* конфигурацию сборки;
* связанные стили.

Определи:

1. какие крупные пользовательские экраны существуют;
2. какое состояние относится только к каждому экрану;
3. какое состояние действительно является общим;
4. какие функции используются только одним экраном;
5. какие модальные окна логически принадлежат определённому экрану;
6. какие действия зависят от выбранной заявки;
7. какие CSS-правила могут безопасно переехать вместе с компонентами;
8. какие связи между частями приложения нельзя разрывать без риска регрессии.

После анализа кратко зафиксируй план декомпозиции, а затем реализуй его.

## Целевая структура

Используй эту структуру как ориентир, но скорректируй её, если фактический код показывает более естественные границы:

```text
frontend/src/
├── App.vue
├── components/
│   ├── AuthScreen.vue
│   ├── RequestRegistry.vue
│   ├── RequestDetails.vue
│   └── AdminPanel.vue
├── api.js
├── registry.js
├── requestDeepLink.js
└── main.js
```

Допускается выделить из `RequestDetails.vue` не более трёх крупных блоков, если компонент иначе остаётся чрезмерно большим:

```text
components/
├── RequestActions.vue
├── RequestDocuments.vue
└── RequestTimeline.vue
```

Не создавай эти компоненты автоматически. Сначала проверь, существуют ли в коде соответствующие естественные границы.

## Распределение ответственности

### `App.vue`

После рефакторинга должен отвечать преимущественно за:

* первоначальную загрузку приложения;
* текущего пользователя и состояние авторизации;
* выбор основного экрана;
* выбранную заявку, если это действительно нужно на верхнем уровне;
* координацию переходов между реестром, карточкой и администрированием;
* существующую синхронизацию с URL.

Не оставляй в `App.vue`:

* формы отдельных workflow-операций;
* загрузку документов;
* пагинацию комментариев;
* состояние административных форм;
* фильтры реестра;
* многочисленные loading/error-переменные отдельных функций.

Ориентир размера после декомпозиции — до 300–400 строк, но не сокращай файл искусственно только ради числа.

### `AuthScreen.vue`

Должен содержать:

* форму входа;
* локальные поля авторизации;
* локальные loading/error;
* emit успешной авторизации.

Не меняй текущую механику авторизации.

### `RequestRegistry.vue`

Должен содержать:

* фильтры;
* сортировку;
* пагинацию;
* загрузку списка;
* состояние загрузки и ошибки реестра;
* отображение списка;
* событие выбора заявки;
* создание заявки, если форма создания фактически является частью реестра.

Не переносить состояние реестра в глобальный store.

### `RequestDetails.vue`

Должен содержать:

* загрузку и отображение карточки;
* workflow-действия;
* комментарии;
* документы;
* локальные формы и модальные окна;
* refresh карточки после операций;
* собственные loading/error-состояния.

При необходимости раздели его только на несколько крупных смысловых частей. Не делай отдельный компонент для каждого workflow-action.

### `AdminPanel.vue`

Должен содержать:

* административные списки и формы;
* локальную загрузку;
* локальные ошибки;
* административные API-операции.

Административное состояние не должно оставаться в `App.vue`.

## Props и events

Старайся использовать короткие и понятные контракты.

Хороший пример:

```vue
<RequestRegistry
  @select-request="openRequest"
  @logout="logout"
/>
```

или:

```vue
<RequestDetails
  :request-id="selectedRequestId"
  @close="closeRequest"
  @updated="handleRequestUpdated"
/>
```

Избегай компонентов с 15–30 props.

Если компоненту требуется слишком много данных верхнего уровня, сначала проверь, не должен ли он самостоятельно загружать и хранить своё локальное состояние.

Не используй двусторонние связи между дочерними компонентами.

## Работа с API

На первом этапе не нужно обязательно дробить `api.js`.

Можно переместить API по отдельным модулям только в случае, если это явно уменьшает код и не расширяет объём PR.

Не меняй:

* URL endpoints;
* HTTP methods;
* payload;
* response mapping;
* обработку CSRF/session;
* существующую семантику ошибок.

## Состояния операций

Сохрани текущую защиту от:

* повторной отправки запросов;
* параллельных конфликтующих операций;
* устаревших ответов;
* работы с уже закрытой карточкой;
* optimistic locking;
* повторного открытия одной заявки.

Не объединяй все loading-состояния в один глобальный `loading`.

Разрешено создать небольшой локальный helper для operation guards, только если он удаляет существенное дублирование и остаётся понятнее текущего кода.

## URL и deep links

На этом этапе не внедряй Vue Router.

Сохрани существующую механику:

* открытие заявки по URL;
* обновление URL при выборе заявки;
* очистка URL при возврате в реестр;
* обработку Back/Forward;
* прямые ссылки из уведомлений.

Логику `requestDeepLink.js` не переписывай без необходимости.

После декомпозиции укажи, какие части самописной навигации позднее можно будет заменить Vue Router.

## CSS

Сохрани текущий внешний вид.

Предпочтительно:

* переносить локальные стили вместе с компонентом;
* оставлять действительно глобальные стили глобальными;
* не переименовывать массово CSS-классы;
* не менять дизайн;
* не делать косметический рефакторинг одновременно с декомпозицией.

Проверь, не перестают ли scoped-стили влиять на вложенные компоненты после переноса шаблона. При необходимости перенеси соответствующие правила в правильный компонент.

## Последовательность выполнения

Работай небольшими логическими шагами:

1. Зафиксируй текущее поведение тестами или проверь существующее покрытие.
2. Выдели `AuthScreen.vue`.
3. Выдели `AdminPanel.vue`.
4. Выдели `RequestRegistry.vue`.
5. Выдели `RequestDetails.vue`.
6. Только после этого оцени необходимость дополнительных крупных компонентов.
7. Очисти `App.vue` от неиспользуемых импортов, refs, computed и handlers.
8. Запусти линтеры, unit-тесты, сборку и доступные E2E-тесты.
9. Исправь документацию, только если она непосредственно описывает изменённую frontend-структуру.

После каждого этапа приложение должно оставаться работоспособным.

## Требования к тестированию

Обязательно запусти доступные команды проекта для:

* ESLint;
* frontend unit tests;
* production build;
* Playwright или другого E2E-набора.

Не изменяй тесты просто для того, чтобы скрыть регрессию.

Добавь или скорректируй тесты для следующих сценариев, если они не покрыты:

* успешная и неуспешная авторизация;
* загрузка реестра;
* применение фильтра;
* открытие карточки;
* возврат из карточки;
* открытие заявки по прямой ссылке;
* Back/Forward браузера;
* выполнение одного основного workflow-действия;
* загрузка документа;
* добавление комментария;
* открытие административного раздела.

Для тестов компонентов проверяй поведение, а не внутренние детали реализации.

## Критерии готовности

Рефакторинг считается завершённым, если:

* внешний вид и пользовательское поведение не изменились;
* backend API не изменён;
* `App.vue` содержит только верхнеуровневую координацию;
* состояние реестра находится в `RequestRegistry.vue`;
* состояние карточки находится в `RequestDetails.vue`;
* административное состояние находится в `AdminPanel.vue`;
* форма входа находится в `AuthScreen.vue`;
* нет компонента с чрезмерным количеством props;
* не появилось десятков микрокомпонентов;
* не добавлены Pinia, TypeScript и Feature-Sliced Design;
* deep links и browser history работают как раньше;
* линтер, тесты и production build проходят;
* в коде не осталось неиспользуемых refs, функций и импортов;
* суммарная когнитивная сложность уменьшилась, а не просто распределилась по новым файлам.

## Что предоставить в результате

После внесения изменений выдай отчёт:

### 1. Фактическая декомпозиция

Таблица:

| Компонент | Ответственность | Локальное состояние | Входы и события |
| --------- | --------------- | ------------------- | --------------- |

### 2. Изменённые файлы

Для каждого файла кратко укажи:

* что перенесено;
* что удалено;
* почему выбрана такая граница.

### 3. Что сознательно не декомпозировано

Перечисли крупные блоки, которые оставлены вместе, и объясни почему их разделение сейчас увеличило бы сложность.

### 4. Проверки

Укажи реальные результаты:

* lint;
* unit tests;
* build;
* E2E.

Не утверждай, что проверка прошла, если команда не запускалась или завершилась ошибкой.

### 5. Метрики до и после

Укажи:

* число строк `App.vue` до и после;
* число новых компонентов;
* самый крупный компонент после рефакторинга;
* число props у каждого крупного компонента;
* удалённые строки дублирования или неиспользуемого кода.

### 6. Оставшийся технический долг

Отдельно перечисли:

* что ещё затрудняет работу с frontend;
* нужен ли в дальнейшем Vue Router;
* есть ли реальные основания для composables;
* есть ли реальные основания для Pinia или TypeScript.

Главный принцип: выбирай минимальное изменение, которое делает код проще. Не подменяй декомпозицию внедрением новой frontend-архитектуры.
