# Инженерный стандарт проекта

## Цели

Проект должен быть понятен новой команде без устных знаний, воспроизводимо
собираться в закрытом контуре и безопасно изменяться через автоматические тесты.

## Структура документации

- README — назначение и быстрый старт;
- product specification — согласованное поведение продукта;
- business rules — стабильные идентификаторы правил;
- architecture — границы модулей и модель данных;
- ADR — почему приняты значимые архитектурные решения;
- OpenAPI — исполняемый контракт HTTP API;
- runbooks — развёртывание, обновление, откат, backup/restore и аварии;
- changelog — пользовательские изменения релизов;
- acceptance features — читаемые бизнесом сценарии.

Документация изменяется в том же merge request, что и затрагивающий её код.

## Код

- backend следует PSR-12 и разделяет domain/application/infrastructure/interface;
- бизнес-правила не размещаются в контроллерах и ActiveRecord callbacks;
- переход статуса является отдельной командой, а не произвольным обновлением поля;
- frontend использует TypeScript strict mode и выделенный слой API;
- даты хранятся в UTC, отображаются в `Europe/Moscow`;
- публичные методы и сложные структуры имеют PHPDoc/TSDoc;
- комментарии объясняют причину, инвариант или внешний контракт;
- очевидные действия не пересказываются комментариями;
- временное решение содержит ссылку на задачу и условие удаления.

## Архитектурные решения

Значимое решение оформляется в `docs/adr/NNNN-title.md` со статусом, контекстом,
решением и последствиями. ADR требуется для изменения workflow, модели доступа,
хранения документов, интеграции и deployment topology.

## Тесты

- ошибка сначала воспроизводится падающим тестом;
- новая бизнес-логика связывается с идентификатором правила;
- тест проверяет наблюдаемое поведение, а не внутреннюю реализацию;
- тесты независимы от порядка запуска и реального времени;
- запрещено обращаться к рабочим LDAP, SMTP и файловому хранилищу из тестов;
- flaky test считается дефектом и не отключается без ADR/задачи;
- критические правила имеют позитивный, негативный и ролевой сценарии.

## Безопасность

- секреты не коммитятся и не попадают в логи;
- SQL выполняется параметризованно;
- авторизация проверяется на сервере для каждого действия;
- загрузки проверяются по размеру, MIME и допустимому расширению;
- документы хранятся вне web root;
- dependency lock-файлы обязательны;
- журнал аудита очищается от credentials и открытых токенов.

## Merge request

MR должен содержать цель, связанные правила, риски, способ проверки и план отката.
Минимум один reviewer нужен для кода, меняющего workflow, ACL, миграции или CI/CD.
Прямой push в защищённую основную ветку запрещён.

## Definition of Done

Задача готова, если:

1. выполнены критерии приёмки;
2. добавлены/обновлены автоматические тесты;
3. обязательный pipeline зелёный;
4. документация и OpenAPI актуальны;
5. миграция и откат проверены при изменении БД;
6. нет внешних runtime-зависимостей;
7. события аудита и уведомления проверены;
8. изменения доступны в changelog;
9. reviewer подтвердил архитектуру и безопасность.
