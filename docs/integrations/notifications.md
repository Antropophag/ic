# Email-уведомления

Портал уведомляет участников процесса на каждом значимом шаге: регистрация
заявки, назначение исполнителя, поступление отчёта на подготовку заключения,
новый комментарий, публикация заключения, решение СБ. Список событий и
получателей соответствует разделу «Уведомления» `docs/product-spec.md`.

Каждое письмо содержит HTML-кнопку и текстовую ссылку на конкретную заявку
вида `{APP_PUBLIC_URL}/?request=<id>`. После входа портал открывает карточку
напрямую, в том числе если заявка уже не входит в ограниченную выдачу реестра.
`APP_PUBLIC_URL` обязателен для отправки уведомлений и должен содержать внешний
адрес портала, доступный получателям писем.

Отчёт никому конкретно не назначается (ТЗ 4.6/4.7 не описывают такого шага):
письмо о его поступлении уходит сразу всем активным пользователям с ролью
«Эксперт», и первый, кто открывает заявку, берёт её в работу (WF-010).
Письма о поступлении отчёта, о публикации заключения (поступление документов
в СБ, ТЗ 4.9) и о завершении испытаний (ТЗ 4.10) дополнительно содержат
активную ссылку на скачивание соответствующей версии документа без входа в
портал (`GET /api/v1/document-links/{token}/download`, ACL-003..006). Ссылку
можно переслать другому сотруднику — доступ по ней не проверяет личность
получателя, только валидность токена.

## Outbox

Письмо ставится в очередь (`notification_outbox`) в той же транзакции, что и
бизнес-событие (NTF-002): текст и семантические ссылки формируются сразу,
поэтому временная недоступность SMTP не влияет на бизнес-транзакцию (NTF-001).
Для download-ссылок outbox хранит только ID версии документа. Детерминированный
bearer credential формируется обработчиком непосредственно перед SMTP из ID outbox,
ID версии и `DOWNLOAD_LINK_SIGNING_KEY`; в `document_download_links` записывается
только хэш SHA-256. Одно уведомление получает один и тот же credential при
повторе, включая неоднозначную ошибку SMTP, поэтому повтор не инвалидирует
потенциально уже доставленное письмо и не накапливает новые активные ссылки.
Фактическую отправку выполняет Compose-сервис `scheduler` (`compose.yaml`).
Это не отдельное приложение или микросервис: сервис
использует тот же backend-образ и запускает один долгоживущий PHP CLI-процесс:

```bash
php yii notification/work
```

Yii и Composer загружаются один раз на жизненный цикл контейнера. Worker
обрабатывает готовые записи пачками по 20 без паузы между заполненными
пачками; при пустой очереди ждёт 2 секунды, поэтому типичная задержка новой
отправки — до 2 секунд. Временная ошибка итерации логируется, после чего
следующая попытка выполняется через 5 секунд. SIGTERM и SIGINT прекращают
обработку после завершения текущего SMTP-письма: остальные записи уже
выбранной пачки остаются в очереди, новая пачка не берётся. Compose даёт
worker до 15 секунд на штатное завершение.

Команда `php yii notification/send` сохранена для разовой ручной обработки
одной пачки (по умолчанию до 50 записей). Обе команды используют один
`NotificationOutboxProcessor`; параметры worker можно посмотреть через
`php yii help notification/work`.

`next_attempt_at` служит двум целям: как аренда захвата (`status = sending`) —
обработчик, упавший после захвата записи, освобождает её через 5 минут для
повторного захвата, — и как момент следующей попытки после ошибки. Обычный
параллельный захват одной записи предотвращается атомарным переводом в
`sending` и lease. Доставка при этом имеет семантику at-least-once, а не
exactly-once: если SMTP уже принял письмо, но процесс аварийно завершился до
фиксации `sent`, запись будет обработана повторно после истечения lease.
SMTP не предоставляет приложению идемпотентность, поэтому в этом редком
сценарии получатель может увидеть дубликат. После ошибки задержка растёт
экспоненциально (60с, 120с, … до 1 часа); после 5 попыток запись переходит в
`failed` и исключается из автоматического цикла. Для явной разовой повторной
обработки `failed` используется только
`php yii notification/send --includeFailed=1`.

`DOWNLOAD_LINK_SIGNING_KEY` должен быть отдельным стабильным случайным значением
не короче 32 символов и одинаковым у backend и scheduler. Его ротация
инвалидирует ещё не отправленные/повторяемые notification links; уже отправленные
links продолжают проверяться по сохранённому hash.
Migration до изменения schema отклоняет отсутствующее, короткое или оставленное
placeholder-значение, поэтому deployment не запускает приложение с
предсказуемыми credentials или без возможности доставки.
При штатном `make prod-up` backend и scheduler остановлены на время forward
migration, поэтому cleanup выполняется без конкурентной постановки или отправки
legacy rows; после migration все прикладные сервисы запускаются новым образом.

## SMTP

Настройки читаются из переменных окружения: `SMTP_HOST`, `SMTP_PORT`,
`SMTP_SECURE`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_TIMEOUT`,
`SMTP_VERIFY_PEER`,
`MAIL_FROM_ADDRESS`, `MAIL_FROM_NAME`. Пароль хранится только в локальном
`.env.prod` и не должен попадать в Git, логи, PR или задачи.

Timeout сетевых операций SMTP по умолчанию составляет 5 секунд
(`SMTP_TIMEOUT=5`). Проверка TLS-сертификата включена по умолчанию
(`SMTP_VERIFY_PEER=1`).
Внутренний релей использует самоподписанный сертификат, поэтому для него
`.env.example` явно задаёт `SMTP_VERIFY_PEER=0` — это осознанная настройка
конкретного релея, а не поведение кода по умолчанию.

Текущий тестовый ящик `k2mailer@shlz.ru` — временное решение до появления
выделенного адреса для портала.

## Редирект писем на время теста

`NOTIFICATION_TEST_REDIRECT_EMAIL` перенаправляет все исходящие письма на
один ящик, не трогая содержимое `notification_outbox` — там остаётся
настоящий получатель (для аудита и повторной отправки), подменяется только
фактическая отправка через `Mailer`. Тема письма получает префикс с реальным
получателем, тело — заголовок с тем же указанием, чтобы не приходилось
открывать каждое письмо для проверки, кому оно предназначалось.

```env
NOTIFICATION_TEST_REDIRECT_EMAIL=tester@shlz.ru
```

Не задано (по умолчанию, включая `.env.example`) — обычная доставка без
изменений. Переменная предназначена только для ручного тестирования на
development/staging-контуре; в production оставлять пустой.

## Известное ограничение локального контура

Из части сетевых окружений (включая текущий контур разработки) релей
`10.178.69.91:587` принимает TCP-соединение, но сразу закрывает его без
ответа — типичный признак фильтрации по IP на стороне релея. Функциональность
outbox (постановка в очередь, идемпотентный захват с арендой, backoff)
проверена тестами и вручную; фактическая доставка требует проверки с машины,
имеющей доступ к релею (например, целевой машины в корпоративной сети).
