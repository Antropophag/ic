# Интеграция с Bitrix24

Старые заявки читаются из универсального списка Bitrix24 через входящий вебхук
со scope `lists`. Интеграция не вызывает методы изменения Bitrix24.

Секретный базовый URL хранится только в `BITRIX24_WEBHOOK_URL`. Его запрещено
добавлять в Git, логи, PR, задачи и скриншоты. Вебхук должен принадлежать
неадминистративному пользователю с правом чтения исходного списка.

## Безопасная разведка

```bash
COMPOSE_ENV_FILE=.env.prod docker compose -p ic-prod --env-file .env.prod -f compose.yaml exec backend php yii bitrix/inspect --max-pages=1
```

Команда выводит только количество записей, статусы и число вложений. Названия,
описания, ФИО и ссылки на документы не выводятся. Значение `--max-pages=0`
обрабатывает все страницы, оставаясь в read-only режиме.

`DETAIL_TEXT` списка содержит JSON. Маппер использует разрешённый набор полей и
не переносит телефоны, адреса, даты рождения, соцсети и другие избыточные данные
вложенного профиля Bitrix24.

Реальные записи допустимы только в локальной development-БД или в контролируемом
миграционном контуре. Тесты CI используют исключительно синтетические данные.

## Полный снимок перед миграцией

Перед проектированием архивной схемы исходный список сохраняется целиком в
неизменяемый снимок. Это не подписка на события: входящий webhook URL служит
учётными данными для read-only вызовов REST API. Команда использует только
`lists.field.get` и `lists.element.get`.

Снимок содержит исходный `DETAIL_TEXT`, персональные данные и потенциальные
ссылки на файлы. Его запрещено создавать внутри Git working tree, публиковать в
задачах и передавать без шифрования. Команда отклоняет путь, находящийся внутри
обнаруженного Git working tree. На хосте заранее создаётся отдельный каталог,
доступный только UID/GID `10001`, под которым работает backend-контейнер:

```bash
sudo install -d -o 10001 -g 10001 -m 0700 /srv/ic-migration/bitrix24

COMPOSE_ENV_FILE=.env.prod docker compose -p ic-prod --env-file .env.prod \
  -f compose.yaml run --rm --no-deps \
  -v /srv/ic-migration/bitrix24:/export \
  backend php yii bitrix/snapshot \
  --output=/export/snapshot-2026-08-06T120000Z --max-pages=0
```

Имя каталога заменяется фактическим UTC-временем среза. Значение
`--max-pages=0` явно включает все страницы; безопасное значение по умолчанию
равно одной странице. Результат имеет структуру:

```text
snapshot-2026-08-06T120000Z/
├── elements.jsonl
├── fields.json
├── users.json
└── manifest.json
```

Каждая строка `elements.jsonl` содержит один исходный элемент. `fields.json`
сохраняет определения полей списка. `users.json` содержит минимальные профили
уникальных авторов: ID, активность, ФИО, email и должность; прочие поля профиля
не сохраняются. `manifest.json` фиксирует версию формата, источник,
время, количество страниц и записей, размеры и SHA-256 файлов. Webhook URL в
снимок не записывается. Для воспроизводимой пагинации элементы запрашиваются по
возрастанию `ID`. `SELECT` явно включает стандартные поля и все обнаруженные
`PROPERTY_*`, поэтому файловые свойства не зависят от набора полей по умолчанию.
Полный запуск дополнительно сверяет число сохранённых элементов с `total`
Bitrix24 и останавливается, если `total` изменился между страницами. Файлы
создаются с режимом `0600`, каталог — `0700`.

До успешного чтения последней страницы существует только каталог с суффиксом
`.partial`, без `manifest.json`. Такой каталог нельзя использовать для анализа;
после выяснения причины его удаляют либо сохраняют отдельно как свидетельство
сбоя. Готовый каталог не перезаписывается повторным запуском.

После создания снимка его копируют в утверждённое зашифрованное хранилище и
сверяют SHA-256 с `manifest.json`. Исходную и резервную копии удаляют после
приёмки миграции согласно согласованному сроку хранения.

## Офлайн-инвентаризация снимка

Инвентаризация не требует webhook URL и не обращается к Bitrix24 или локальной
БД. Отчёт создаётся рядом со снимком либо в другом закрытом каталоге:

```bash
COMPOSE_ENV_FILE=.env.prod docker compose -p ic-prod --env-file .env.prod \
  -f compose.yaml run --rm --no-deps \
  -v /srv/ic-migration/bitrix24:/export \
  backend php yii bitrix/inventory \
  --snapshot=/export/snapshot-2026-08-06T120000Z \
  --output=/export/inventory-2026-08-06T120000Z.json
```

До анализа команда проверяет SHA-256 `fields.json`, `elements.jsonl` и, для
снимка формата 2, `users.json`, а также
число записей из manifest. Существующий отчёт не перезаписывается; временный
файл публикуется атомарно и имеет режим `0600`.

Отчёт содержит:

- полный словарь статусов и их количества;
- авторитетный архивный номер `ID`, его high-water mark, диапазон, дубли и
  пропуски; `CODE`, `NAME` и подходящие скалярные поля `DETAIL_TEXT` остаются в
  отчёте как диагностические кандидаты;
- терминальные заявки первой волны и полный список отложенных заявок с номером
  и исходным статусом;
- дубли исходных ID и элементы с некорректным `DETAIL_TEXT`;
- только структуру `supportingDocFiles`, `reportFiles` и `PROPERTY_648`: типы,
  количество и наборы ключей объектов без имён, значений и URL;
- перечень кодов `PROPERTY_*` из определения списка.

Числовые значения кандидатов номера и исходные ID не считаются персональными
данными, но отчёт всё равно хранится в закрытом миграционном каталоге. Значения
нечисловых кандидатов намеренно не выводятся: до подтверждения поля они могут
оказаться названием или другим пользовательским текстом.

Фактическая сверка с интерфейсом Bitrix24 подтвердила, что отображаемый номер
заявки равен `ID` элемента. Статус `Заявка отозвана` является терминальным и
входит в первую волну вместе с выполненными и отказанными заявками. `Черновик` и
прочие незавершённые состояния остаются в Bitrix24 до терминального перехода.

Снимок не является транзакционным срезом Bitrix24. Предпочтительно остановить
создание и изменение заявок до его запуска. Если это невозможно, выполняют два
полных снимка после организационного момента среза и сравнивают количество,
диапазон/дубли номеров и распределение статусов; любое расхождение требует
отдельной проверки исходных элементов до фиксации high-water mark.

Результат полного среза от 2026-08-06 зафиксирован в
[отчёте инвентаризации](bitrix24-inventory-2026-08-06.md).
Граница готовности этапа и оставшиеся работы перечислены в
[статусе подготовки миграции](bitrix24-migration-status-2026-08-06.md).

## Выгрузка файлов через браузерную OAuth-сессию

Фактические ссылки из `DETAIL_TEXT` ведут не в файловое свойство списка, а в
защищённый каталог старого приложения `/docs/file/FilesProposalTest/`. Входящий
webhook авторизует REST API, но не этот HTTP endpoint. Неавторизованный запрос
перенаправляется на OAuth, поэтому для одноразовой миграции используется
изолированный Chromium-профиль.

Авторизация запускается из графического терминала пользователя. Snapshot и
workspace должны находиться вне Git:

```bash
cd /path/to/ic
npm --prefix frontend run bitrix-files -- auth \
  --snapshot=/srv/ic-migration/bitrix24/snapshot-YYYYMMDDTHHMMSSZ \
  --workspace=/srv/ic-migration/bitrix24/files-YYYYMMDD
```

В открывшемся окне нужно войти в Bitrix24, завершить OAuth и вернуться в
терминал, не закрывая браузер. После Enter команда проверит доступ к одному
файлу и закроет профиль. Пароль не считывается инструментом. Профиль содержит
cookies и токены, поэтому каталог и все его файлы принудительно получают права
`0700/0600`, не архивируются и удаляются после приёмки.

Сначала выполняется пилот на десяти уникальных файлах:

```bash
npm --prefix frontend run bitrix-files -- download \
  --snapshot=/srv/ic-migration/bitrix24/snapshot-YYYYMMDDTHHMMSSZ \
  --workspace=/srv/ic-migration/bitrix24/files-YYYYMMDD \
  --limit=10 --max-bytes=1073741824
```

После проверки пилота полный возобновляемый запуск выполняется без `--limit`.
Параметр `--max-bytes` задаёт жёсткий предел одного исторического файла; значение
по умолчанию — 1 ГиБ. Это защитный предел выгрузки, а не разрешение импортировать
такой файл в приложение.

Downloader:

- проверяет manifest и SHA-256 JSONL до чтения;
- принимает только HTTPS, исходный host и каталог
  `/docs/file/FilesProposalTest/`, запрещает credentials и query string;
- корректно кодирует пробелы, кириллицу и `#` в старых URL;
- при `403/404` перебирает варианты с восстановлением одного потерянного `+` в
  имени; два подтверждённых многосимвольных искажения нормализуются до перебора;
- передаёт только cookies из изолированного профиля и не пишет URL в отчёт;
- открывает карточку файла и использует штатную ссылку Bitrix24
  `/disk/downloadFile/...`, не извлекая OAuth-токены из браузера;
- скачивает 8484 уникальных объекта вместо повторения всех 8534 связей;
- пишет потоково в файл `.partial` с лимитами времени и размера;
- атомарно публикует объект и сохраняет размер, MIME браузерной загрузки и SHA-256 в
  `checkpoint.jsonl`;
- при resume перепроверяет размер и SHA-256 уже скачанного объекта;
- останавливает полный цикл при OAuth redirect;
- сохраняет безопасный `associations.jsonl` без URL для восстановления связей с
  заявками.

После полной выгрузки выполняется офлайн-проверка без браузера и Bitrix24:

```bash
npm --prefix frontend run bitrix-files -- verify \
  --snapshot=/srv/ic-migration/bitrix24/snapshot-YYYYMMDDTHHMMSSZ \
  --workspace=/srv/ic-migration/bitrix24/files-YYYYMMDD
```

Команда требует точного совпадения всех записей `associations.jsonl` со
snapshot, всех файловых ID в `objects/` и успешных checkpoint-записей, а затем
повторно вычисляет размер и SHA-256 каждого объекта.

`checkpoint.jsonl`, `associations.jsonl`, `objects/` и `browser-profile/`
содержат миграционные либо авторизационные данные и никогда не коммитятся.

## Импорт в локальную БД

Команда импорта по умолчанию выполняет dry-run и не меняет БД:

```bash
COMPOSE_ENV_FILE=.env.dev docker compose -p ic-dev --env-file .env.dev \
  -f compose.yaml -f compose.dev.yaml exec backend php yii bitrix/import --max-pages=1
```

Webhook должен иметь права чтения списков и пользователей. До валидации заявок
команда получает каждого уникального автора методом `user.get`. Email
нормализуется в нижний регистр, а его часть до `@` используется как
`users.ad_login`; имя строится из `LAST_NAME`, `NAME`, `SECOND_NAME`. Отсутствие
пользователя, email, имени/фамилии, небезопасный login или совпадение login у
двух Bitrix-пользователей останавливает команду до изменения БД.

Новый активный пользователь Bitrix24 создаётся активным с базовой ролью
`employee`, неактивный — заблокированным без роли. Если профиль с таким
`ad_login` уже существует, импорт использует его как автора, но не меняет его
данные, активность и роли: профиль мог быть ранее синхронизирован из AD.

Запись включается только явным параметром:

```bash
COMPOSE_ENV_FILE=.env.dev docker compose -p ic-dev --env-file .env.dev \
  -f compose.yaml -f compose.dev.yaml exec backend php yii bitrix/import --max-pages=1 --apply=1
```

Значение должно быть ровно `1`. Любое другое значение, кроме безопасного `0`,
отклоняется с ошибкой использования до чтения и записи данных.

Повторный запуск пропускает заявки с тем же `legacy_id`. Команда возвращает
ненулевой код, если часть исходных записей не прошла строгую нормализацию, даже
когда остальные записи были импортированы.
