# Передача в локальную инфраструктуру АО «ЩЛЗ»

## Принцип

Приложение проектируется как полностью автономное on-premise решение. В runtime
оно не обращается к инфраструктуре разработчика, публичным CDN, Google Fonts,
внешним API, облачным хранилищам или внешним сервисам авторизации.

## Что передаётся

- единый Git-репозиторий с backend, frontend, миграциями и документацией;
- `Dockerfile` с фиксированными версиями;
- `compose.yaml` для тестового контура;
- `.gitlab-ci.yml` без привязки к публичному GitLab;
- шаблон переменных окружения без секретов;
- SQL-миграции и импортёр Bitrix24;
- инструкции развёртывания, обновления, отката и резервного копирования;
- контрольные суммы релизных артефактов.

## Перенос Git

Предпочтительный путь после предоставления адреса локального GitLab:

```bash
git remote add corporate <URL локального GitLab>
git push corporate --all
git push corporate --tags
```

Если между сетями нет маршрута, создаётся переносимый bundle:

```bash
git bundle create shlz-test-registry.bundle --all
git clone shlz-test-registry.bundle shlz-test-registry
```

Bundle содержит ветки, теги и историю и переносится разрешённым корпоративным
способом. Секреты в него не включаются.

## CI/CD локального GitLab

Pipeline состоит из независимых стадий:

1. lint;
2. backend tests;
3. frontend tests;
4. production build;
5. сборка контейнеров;
6. публикация в локальный GitLab Container Registry;
7. ручное развёртывание на test;
8. ручное подтверждение production.

Доступ к production не требуется разработчику: pipeline выполняется локальным
GitLab Runner под контролем предприятия.

## Зависимости в закрытой сети

На этапе обследования нужно определить, имеет ли GitLab Runner доступ к интернету.

- при наличии доступа Composer и npm используют lock-файлы и проверку целостности;
- без доступа зависимости зеркалируются во внутренний Composer/npm proxy либо
  доставляются как предварительно собранные контейнерные слои;
- базовые Docker-образы импортируются в локальный Container Registry;
- шрифты и UI-ассеты входят в frontend bundle;
- production-сборка не загружает ресурсы из интернета.

Каталоги `vendor` и `node_modules` не становятся источником истины и не заменяют
lock-файлы. Для изолированной среды формируется документированный пакет зависимостей.

## Конфигурация и секреты

- в Git хранится только `.env.example`, рабочая production-конфигурация — `.env.prod`;
- LDAP, MariaDB, SMTP и ключи приложения задаются protected/masked variables GitLab;
- отдельные значения используются для test и production;
- файлы приложения неизменны между средами;
- миграции запускаются отдельной контролируемой job перед переключением версии.

## Варианты эксплуатации

Основной вариант — контейнеры в локальном Registry. Если Docker на production
запрещён, сохраняется классическая схема Nginx + PHP-FPM + MariaDB: frontend
собирается в статические файлы, backend разворачивается из release-архива.
Бизнес-код и схема БД от способа развёртывания не зависят.

## Обновление и откат

- релизы маркируются Git-тегами;
- контейнеры и архивы неизменяемы и имеют номер версии;
- перед миграциями создаётся резервная копия БД;
- backward-compatible миграции применяются до переключения приложения;
- откат приложения выполняется на предыдущий образ/архив;
- необратимые миграции выпускаются отдельным согласованным этапом.

## Данные для уточнения у инфраструктурной команды

- URL и версия локального GitLab;
- наличие и тип GitLab Runner;
- наличие Container Registry;
- доступ Runner к Composer/npm/Docker Hub либо внутренние зеркала;
- допустимы ли Docker/Podman на test и production;
- целевая ОС, Nginx, PHP и MariaDB;
- способ передачи секретов;
- SMTP relay, DNS-имя и TLS-сертификат портала;
- каталоги/тома для документов и резервных копий.

Отсутствие этих ответов не блокирует разработку: интерфейсы конфигурации и pipeline
готовятся заранее, а конкретные адреса и способы доставки подставляются при передаче.
