# Бизнес-правила

Идентификаторы правил стабильны и используются в коде, тестах, задачах и отчётах
приёмки. Изменение правила требует изменения связанного теста и документации.

## Пользователи и доступ

- **AUTH-001:** успешно прошедший LDAP bind сотрудник может войти в портал.
- **AUTH-002:** при первом входе создаётся локальный профиль с базовой ролью `Сотрудник`.
- **AUTH-003:** отключённый локальный профиль не получает доступ даже при успешном bind.
- **AUTH-004:** специальные роли хранятся локально и не удаляются при обновлении профиля из AD.
- **AUTH-005:** пользователь может иметь несколько специальных ролей.
- **AUTH-006:** одна заранее созданная локальная техническая identity может
  использоваться только для осознанного аварийного административного входа.
  Локальный пароль проверяется лишь при точном совпадении с настроенным
  break-glass логином; остальные логины остаются LDAP-only. Секрет хранится
  только как стойкий hash вне БД, а успешные и отклонённые попытки попадают в
  аудит.
- **AUTH-007:** назначать роли и заранее заводить локальный
  профиль по `ad_login` до первого входа сотрудника, может только активный
  пользователь с ролью `Администратор`. Право управлять процессными ролями
  (WF-001 и т.д.) не даёт права менять RBAC — иначе руководитель ИЦ мог бы
  сам себе выдать любую роль. Отзыв роли доступен тому же администратору только
  с обязательной причиной; изменение и аудит причины выполняются атомарно.
- **AUTH-008:** при миграции Bitrix24 `ad_login` автора определяется как
  нормализованная часть уникального email до `@`; активный автор заранее
  получает локальный профиль и базовую роль, неактивный — заблокированный
  профиль без роли. Уже существующий локальный профиль импорт не изменяет.

## Регистрация заявки

- **IDEM-001:** успешный повтор production POST-команды с тем же
  `Idempotency-Key`, actor, HTTP method, нормализованным `pathInfo` без query
  string и содержимым возвращает исходный результат и не повторяет доменное
  изменение, аудит, файл или постановку уведомления.
- **IDEM-002:** один ключ нельзя использовать для другого содержимого; ошибки и
  rollback не занимают ключ, а replay хранится 24 часа. JSON сравнивается в
  canonical форме, multipart — по полям и фактическому содержимому всех файлов.

- **REQ-001:** заявку может создать сотрудник, не являющийся исполнителем ИЦ,
  руководителем ИЦ или руководителем лаборатории. Для этих ролей в реестре
  скрыты вкладка «Мои заявки» и кнопка «Новая заявка».
- **REQ-002:** номер заявки уникален, монотонно возрастает и назначается транзакционно.
- **REQ-003:** дата, инициатор и подразделение берутся из серверного контекста.
- **REQ-004:** обязательны наименование, производитель, поставщик, количество и метод испытаний.
- **REQ-005:** количество образцов — положительное целое число.
- **REQ-006:** зарегистрированные исходные поля заявки не редактируются.
- **REQ-007:** новая заявка получает статус `Заявка зарегистрирована`.
- **REQ-008:** руководители ИЦ и лаборатории уведомляются после успешной регистрации.
- **REQ-009:** инициатор отдельным письмом уведомляется о приёме его заявки —
  подтверждение, что заявка зарегистрирована и попала в процесс, без ожидания
  следующего шага испытательного центра.
- **REQ-010:** подразделение заявки сохраняется как исторический снимок из
  серверного профиля инициатора в момент регистрации; отсутствие подразделения
  блокирует создание новой заявки. Последующее изменение профиля не меняет
  ранее созданные заявки. Legacy-значение может отсутствовать и тогда
  отображается как «Подразделение не указано».
- **REQ-011:** изменить снимок подразделения отдельной заявки может только
  активный администратор. Изменение выполняется с optimistic lock, очищает
  недостоверный внешний ID, помечается источником `manual` и записывается в
  аудит событием `request.department_changed`, не являющимся переходом workflow.

## Назначения и статусы

- **WF-001:** исполнителя назначает руководитель ИЦ или лаборатории.
- **WF-002:** назначить можно только активного пользователя с ролью `Исполнитель ИЦ`.
- **WF-003:** все переходы выполняются только по разрешённому графу и проверяются сервером.
- **WF-004:** в работу переводит исполнитель либо руководитель ИЦ/лаборатории.
- **WF-005:** приостановить и возобновить работу может исполнитель либо руководитель;
  для приостановки обязательна причина, для возобновления — нет; карточка
  приостановленной заявки показывает причину последнего действующего перехода
  `suspend`, а после возобновления её не показывает.
- **WF-005A:** возраст текущего состояния считается от последнего перехода в
  текущий статус (при отсутствии перехода — от создания), а последнее изменение
  — по максимуму `requests.updated_at` и времени успешного пользовательского
  audit-события заявки; чтение, скачивание, отклонённые действия и технические
  события эти значения не меняют.
- **WF-005B:** инициатору явно показывается отсутствие требуемого следующего
  шага, если backend не предоставляет ему формализованного обязательного
  процессного действия; право добровольно отозвать заявку не считается таким шагом.
- **WF-006:** отказ оформить может только руководитель ИЦ или лаборатории и
  только с обязательной причиной.
- **WF-007:** инициатор может отозвать незавершённую заявку до решения СБ только
  с обязательной причиной.
- **WF-008:** каждый переход сохраняет автора, время, исходный и новый статус и причину.
- **WF-009:** цветовая метка не является статусом и изменяется только руководителями.
  В интерфейсе метка кодируется насыщенной точкой и полосой строки, а
  статус — отдельной мягкой капсулой без маркера; текст капсулы темнее фона того же
  семантического оттенка.
- **WF-010:** любой активный пользователь с ролью `Эксперт` сам берёт заявку на
  подготовку заключения в работу (self-assign), включая заявку, уже
  закреплённую за другим экспертом (перехват, например на время отпуска), —
  руководитель эксперта не назначает (ТЗ 4.6/4.7 не описывают такого шага).
  Взять заявку, уже закреплённую за собой, повторно нельзя.
- **WF-011:** эксперт, которому назначена заявка, может явно передать её
  другому конкретному активному пользователю с ролью `Эксперт`, кроме самого
  себя. Перехват заявки у третьего эксперта — это self-assign по WF-010, а
  не переназначение.
- **WF-012:** руководитель ИЦ или лаборатории может переназначить исполнителя
  не только для зарегистрированной заявки, но и после начала работы, пока
  заявка в статусе `Заявка зарегистрирована`, `В работе` или `Работы
  приостановлены`. Переназначение не меняет статус заявки, закрывает
  предыдущее назначение и уведомляет только нового исполнителя — по аналогии
  с WF-011 (issue #72). Письмо о назначении отражает фактический статус
  заявки: для уже начатой или приостановленной работы текст не предлагает
  «принять её в работу».
- **WF-013:** назначение исполнителя, уже закреплённого за заявкой, отклоняется
  как no-op — действие не меняет назначение, но без этой проверки всё равно
  закрывало бы и заново открывало запись в `request_assignments`, увеличивало
  `lockVersion` и отправляло письмо без реального изменения.

## Комментарии и вложения

- **COM-001:** комментарии разрешены от регистрации до решения СБ включительно.
- **COM-002:** комментарий после отправки не редактируется и не удаляется обычным пользователем.
- **COM-003:** автор, дата и время комментария назначаются сервером.
- **COM-004:** вложения комментария наследуют доступ комментария.
- **COM-005:** комментарии и их вложения видят все авторизованные сотрудники.
- **COM-006:** участники процесса уведомляются о новом комментарии через очередь.
- **COM-007:** вложение ограничено 200 МБ; расширение и определённый сервером MIME
  должны входить в разрешённую пару, DOCX/XLSX проходят проверку структуры и
  распакованного размера, а физический путь не зависит от имени файла.

## Отчёт и заключение

- **DOC-001:** отчёт загружает назначенный исполнитель либо руководитель ИЦ/лаборатории.
- **DOC-002:** первая загрузка отчёта переводит заявку в `Подготовка заключения`.
- **DOC-002A:** отчёт принимается в PDF размером до 200 МБ; отклонённые по формату,
  MIME, расширению, размеру или отсутствию файла загрузки журналируются этим правилом.
  Сохранение первой версии и увеличение `lockVersion`, а при необходимости и
  переход статуса, выполняются одной транзакцией под блокировкой заявки.
- **DOC-003:** до завершения заявки отчёт доступен через обычный интерфейс только
  назначенному исполнителю, руководителю ИЦ/лаборатории и эксперту, закреплённому
  за заявкой (иначе эксперт не может сформировать заключение) — остальным
  сотрудникам недоступен.
- **DOC-004:** для каждой ревизии существует не более одного актуального заключения;
  публикация версии, переход статуса и аудит выполняются одной транзакцией.
- **DOC-005:** заключение готовит пользователь, назначенный экспертом заявки.
- **DOC-006:** PDF содержит сведения заявки, текст, дату, ФИО и должность эксперта.
- **DOC-007:** публикация заключения переводит заявку в `Контроль СБ`.
- **DOC-008:** замена отчёта создаёт новую ревизию и не уничтожает старую.
- **DOC-009:** после возврата СБ новое заключение готовит тот же эксперт.
- **DOC-010:** старые ревизии отображаются в истории версий и доступны только
  их авторам и пользователям с процессной ролью руководителя или сотрудника СБ.
- **DOC-011:** назначенный исполнитель или руководитель ИЦ/лаборатории может удалить
  загруженный отчёт независимо от текущего статуса заявки (в т. ч. после `Заявка
  выполнена`, ТЗ 7.8); удалённый отчёт и все его ревизии перестают быть доступны
  для скачивания как через портал, так и по ранее выданным email-ссылкам. Удаление
  требует обязательной причины, сразу переводит заявку в `Заявка в работе` и
  сохраняется в аудите и ленте заявки.
- **DOC-012:** повторная загрузка отчёта после удаления по DOC-011 запускает цикл
  эксперт → СБ заново — статус переходит в `Подготовка заключения`, даже если
  заявка уже была выполнена; уникальный документ `request_documents` переиспользуется
  (снимается признак удаления), а не создаётся заново. Версии отчёта, загруженные
  до удаления, остаются недоступны безвозвратно — восстанавливается только сам
  документ, а не ранее удалённые ревизии и выданные на них email-ссылки; новая
  версия, загруженная после восстановления, доступна как обычно.
- **DOC-013:** назначенный исполнитель либо руководитель ИЦ/лаборатории может
  сформировать редактируемый DOCX-черновик акта испытаний по приложению В СТО СМК
  241.2-2024 в состояниях `Заявка в работе` и `Подготовка заключения`, а также в
  состоянии `Заявка выполнена`, если после удаления отсутствует действующий отчёт.
  Генерация использует актуальные
  сведения заявки, не меняет заявку, статус и `lockVersion`, не создаёт документ
  или его версию и не заменяет штатную загрузку утверждённого PDF-отчёта.

## Контроль СБ

- **SEC-001:** решение СБ может принять только активный пользователь с ролью `Сотрудник СБ`.
- **SEC-002:** `✓` без причины переводит заявку в `Заявка выполнена`; непустая
  причина для согласования запрещена.
- **SEC-003:** `✕` переводит заявку в `Заявка в работе` и сохраняет комментарий причины.
- **SEC-004:** после `✕` сохраняются прежние исполнитель и эксперт.
- **SEC-005:** новая ревизия после `✕` проходит полный цикл эксперт → СБ.

## Персональные очереди действий

- **DASH-009:** operational workload ИЦ включает только заявки в статусах
  `registered`, `in_progress` и `suspended`; `active` равен сумме `unassigned`
  (`registered` без текущего исполнителя), `ready_to_start` (`registered` с текущим
  исполнителем), `in_progress` и `suspended`.
- **DASH-014:** заголовок operational summary дополнительно показывает независимые
  счётчики заявок на экспертизе (`opinion_preparation`) и контроле СБ
  (`security_review`); персональная детализация для этих стадий не выводится.
- **DASH-010:** operational summary доступна всем аутентифицированным пользователям
  порта и возвращается backend независимо от роли. Поимённый состав исполнителей
  возвращается и показывается только ролям `ic_manager` и `laboratory_manager`.
- **DASH-011:** до появления отдельного структурированного поля направления
  operational workload временно выводит направление из пользовательской цветовой метки:
  `blue` — механические, `orange` — метрологические, `violet` — электротехнические
  испытания, любые остальные, неизвестные и отсутствующие значения — «Без направления».
  Это compatibility/product mapping для представления, а не исторический доменный факт.
  Внутри направления учитываются
  только current assignments в operational-статусах; назначения недоступным
  пользователям остаются в итогах как «Недоступный исполнитель». Для каждого
  исполнителя отдельно возвращаются числа заявок в `in_progress` и `suspended`,
  а заявки без текущего назначения учитываются в `unassigned` направления.

- **DASH-001:** категория dashboard содержит только заявки, для которых активный
  текущий пользователь может выполнить названное процессное действие с учётом
  статуса, ролей и текущих назначений; наличие роли само по себе не расширяет
  доступ и не заменяет проверку действия backend. Категории с нулевым числом
  доступных заявок не возвращаются и не отображаются.
- **DASH-002:** «Назначить исполнителя» содержит зарегистрированные заявки без
  текущего исполнителя для руководителя ИЦ или лаборатории.
- **DASH-003:** «Начать или возобновить работы» содержит зарегистрированные
  заявки с исполнителем и приостановленные заявки, которые пользователь может
  начать или возобновить по WF-004/WF-005.
- **DASH-004:** «Загрузить отчёт» содержит заявки без действующего отчёта, в
  которых назначенный исполнитель или руководитель может загрузить первый либо
  восстановленный отчёт по DOC-001/DOC-012. Возможность заменить уже
  существующую версию не считается требующей внимания.
- **DASH-005:** экспертная работа разделена на «Взять заявку на экспертизу» по WF-010 и
  «Подготовить заключение» по DOC-005/DOC-007; первая очередь исключает заявки,
  уже закреплённые за текущим экспертом, вторая содержит только их. Отзыв роли
  запрещает брать новую экспертизу, но активный текущий эксперт может завершить
  уже назначенную работу согласно действующей OpinionPolicy.
- **DASH-006:** «Визировать протокол испытаний» содержит заявки, в которых текущий сотрудник СБ
  может принять решение по SEC-001.
- **DASH-007:** счётчики точны для полного персонального scope, не зависят от
  страницы, вкладки, поиска и статусного фильтра. При совмещении ролей одна
  заявка может учитываться в нескольких категориях; суммы не являются числом
  уникальных заявок.
- **DASH-008:** выбранная категория сужает обычный серверный реестр. Поиск и
  статус применяются поверх неё, сортировка сохраняется, страница сбрасывается
  на первую; повторный выбор снимает категорию.

## Доступ к документам и ссылки

- **ACL-001:** после завершения актуальные отчёт и заключение доступны всем авторизованным сотрудникам.
- **ACL-002:** до завершения доступ определяется ролью и текущим этапом.
- **ACL-003:** письма о поступлении отчёта эксперту (ТЗ 4.6), поступлении
  документов в СБ (ТЗ 4.9) и завершении испытаний (ТЗ 4.10) содержат активную
  ссылку на скачивание конкретной версии документа.
- **ACL-004:** ссылка действует без входа в портал, в том числе пока обычный
  доступ к документу через портал ещё не открыт.
- **ACL-005:** токен ссылки криптографически защищён, в БД хранится только хэш;
  хранилище уведомлений может содержать ссылку на версию документа, но не
  bearer credential или полный bearer URL.
- **ACL-006:** ссылку можно переслать другому сотруднику — доступ по ней не
  проверяет личность получателя.
- **ACL-007:** успешные и отклонённые попытки скачивания через авторизованный
  интерфейс портала журналируются.

## Уведомления и аудит

- **NTF-001:** бизнес-транзакция не откатывается из-за временной ошибки SMTP.
- **NTF-002:** уведомление ставится в очередь в той же транзакционной границе через outbox.
- **NTF-003:** атомарный lease предотвращает обычный одновременный захват
  письма; доставка имеет семантику at-least-once, поэтому после аварии между
  успешным SMTP и фиксацией `sent` возможна повторная доставка.
- **AUD-001:** создание, назначение, переход, документ, решение СБ и роли попадают в аудит.
- **AUD-002:** аудит нельзя изменить или удалить через прикладной интерфейс.
- **AUD-003:** аудит не содержит паролей, LDAP credentials и открытых download-токенов.

## Импорт

- **IMP-001:** повторный импорт одной записи не создаёт дубликат заявки.
- **IMP-002:** внешний идентификатор сохраняется как `legacy_id`, а номер
  элемента Bitrix24 — как номер заявки без перенумерации.
- **IMP-003:** неоднородные записи с внутренним `ID` и без него нормализуются одинаково.
- **IMP-004:** избыточные персональные данные не переносятся.
- **IMP-005:** отсутствующий файл отмечается ошибкой импорта, но не теряет заявку.
- **IMP-006:** импорт поддерживает dry-run с отчётом без изменения БД.
- **IMP-007:** полный снимок Bitrix24 создаётся только read-only методами,
  публикуется после завершения всех страниц и содержит контрольные суммы.
- **IMP-008:** инвентаризация выполняется офлайн, проверяет целостность снимка и
  не раскрывает значения пользовательских полей и URL файлов в отчёте.
- **IMP-009:** архивный номер заявки равен `ID` элемента Bitrix24; максимальный
  импортированный `ID` поднимает локальную последовательность номеров, но импорт
  меньшего номера не может её уменьшить.
- **IMP-010:** выполненные, отказанные и отозванные заявки входят в первую
  терминальную волну; остальные статусы переносятся только после завершения.
- **IMP-011:** выгрузка файлов дедуплицируется по исходному файловому ID,
  возобновляется по checkpoint и не сохраняет OAuth credentials либо URL в
  миграционном отчёте.
- **IMP-012:** до записи заявок импорт получает через `user.get` всех уникальных
  авторов и останавливается при отсутствующем пользователе, email, ФИО,
  некорректном AD login либо неоднозначном соответствии.
- **IMP-013:** импорт сохраняет исходное `countTestItems` без смыслового изменения;
  однозначное положительное целое записывается как количество образцов, а для
  неоднозначного исторического значения количество остаётся неизвестным (`NULL`).
  Конечный набор проверенных вручную конструкций N × M может нормализоваться
  только через версионируемый whitelist, строго сверяемый с исходным snapshot;
  это не является общим правилом разбора пользовательского текста.
- **IMP-014:** legacy import сохраняет `nameType` длиной до 2000 символов без
  обрезания, но создание обычной заявки по-прежнему ограничивает наименование
  500 символами.
- **IMP-015:** при отсутствующем `creator.ID` автор legacy-заявки берётся только
  из структурированного `CREATED_BY`; подтверждённые исправления контрагентов
  применяются через проверяемый CSV и не подменяют непустые исходные значения.
