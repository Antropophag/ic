# Архитектура

## Технологии

- backend: PHP 8.3, Yii2 REST API;
- frontend: Vue 3, TypeScript, Vite, Pinia, Vue Router;
- база: MariaDB;
- инфраструктура: Nginx, PHP-FPM, worker очереди, Docker Compose;
- PDF: серверная генерация из версионируемого HTML-шаблона.

## Модули

- Identity — LDAP-вход, локальные профили, сессии;
- Access — роли и разрешения;
- Requests — заявки и конечный автомат статусов;
- Discussions — комментарии и вложения;
- Documents — закрытое хранилище и версии документов;
- Expertise — экспертное заключение и PDF;
- SecurityControl — решение СБ и возврат на доработку;
- Notifications — очередь и шаблоны email;
- Audit — неизменяемая история действий;
- Import — повторяемый импорт из Bitrix24.

## Первый вертикальный срез

Реализуется цепочка `Vue → Yii2 JSON API → MariaDB`: список заявок и создание
заявки. Номер выдаётся отдельным заблокированным счётчиком, создание заявки и
первой записи истории выполняются одной транзакцией. Временный dev user header
обрабатывается исключительно при `APP_ENV=dev`; вне dev текущий пользователь
определяется LDAP-сессией (см. раздел «LDAP» ниже).

## Второй вертикальный срез

Руководитель ИЦ или лаборатории назначает активного исполнителя ИЦ. Локальные
роли хранятся отдельно от профиля AD, назначение сериализуется блокировкой строки
заявки и сохраняется как новая запись истории. Успешная и запрещённая попытки
фиксируются в общем аудите с идентификатором бизнес-правила.

## Третий вертикальный срез

Назначенная заявка переводится в работу текущим исполнителем или руководителем.
Клиент передаёт `lockVersion`; репозиторий блокирует ту же строку заявки, что и
операция назначения, затем проверяет активность пользователя, роль и актуальное
назначение и делает условный update по статусу и версии. Переход и аудит
сохраняются в той же транзакции, а конфликт версии не затирает более свежее
изменение.

## LDAP

Начальная конфигурация совместима с действующим корпоративным проектом:

```dotenv
LDAP_HOST=10.178.80.80
LDAP_PORT=389
LDAP_DOMAIN=shlz.ru
LDAP_BASE_DN=DC=shlz,DC=ru
LDAP_USE_TLS=false
```

Настройки не зашиваются в код. После ответа IT можно без изменения приложения
включить LDAPS/StartTLS, задать DNS-имена контроллеров и уточнить атрибуты профиля.

`POST /api/v1/auth/login` выполняет простой LDAP bind как `{login}@{LDAP_DOMAIN}`
(UPN-подобный формат) и затем self-lookup `ldap_search` под тем же соединением —
отдельный сервисный аккаунт не заводится (`LdapAuthenticator`,
`NativeLdapClient`). При первом успешном входе создаётся локальный профиль
(AUTH-002) с ролью `Сотрудник`; при повторном — обновляются `display_name`,
`email`, `department`, `position` из AD, но не роли и не `is_active`
(AUTH-004). Отключённый профиль (`is_active = false`) отклоняется даже при
успешном bind — как на входе, так и при каждом следующем запросе уже открытой
сессии (AUTH-003, `CurrentUser::id()` перепроверяет `is_active` в БД на каждый
запрос). Сессия — стандартная Yii-сессия с cookie, `regenerateID(true)` при
входе защищает от session fixation; `enableCsrfValidation` включена вне dev на
всех state-changing контроллерах.

## Файлы и ссылки

- файлы физически находятся вне публичной директории;
- доступ к обычному скачиванию проверяется API;
- имя файла, MIME, размер и SHA-256 сохраняются в БД;
- токен публичной ссылки случаен, в БД хранится только его хэш;
- ссылка относится к одной версии документа и может быть отозвана;
- при замене документа ссылки старой версии отзываются;
- скачивания попадают в аудит.

## Импорт Bitrix24

Экспорт является последовательностью `номер → заголовок → JSON`, а не единым
JSON-массивом. Импорт выполняется в два шага: разбор в нормализованный промежуточный
формат, затем транзакционная загрузка. Из профиля Bitrix24 переносятся только
идентификатор, ФИО, email, должность и подразделение; телефоны, дни рождения и
сведения об активности отбрасываются.

Старый идентификатор сохраняется в `requests.legacy_id`. URL вложений скачиваются
отдельным этапом при наличии авторизованного доступа к Bitrix24.
