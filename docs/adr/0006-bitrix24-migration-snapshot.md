# ADR 0006: Неизменяемый снимок Bitrix24 перед архивной миграцией

## Статус

Принято.

## Контекст

Архивная миграция зависит от фактических номеров, статусов и неоднородных
структур файлов примерно 2477 элементов универсального списка Bitrix24.
Повторная разведка непосредственно через production API не воспроизводима:
источник продолжает меняться, запрос может оборваться между страницами, а
ответы содержат персональные данные и секретные download URL.

Альтернативами были непосредственный импорт из Bitrix24, сохранение только
агрегированного отчёта и полный исходный снимок. Прямой импорт смешивает
разведку с изменением БД. Агрегаты не позволяют повторить маппинг и расследовать
конкретную ошибку без нового обращения к уже изменившемуся источнику.

## Решение

До изменения целевой схемы создаётся полный read-only снимок. Определения полей
и минимизированные профили уникальных авторов хранятся в JSON, элементы —
потоково в JSONL, manifest — отдельно с версией
формата, границами времени, количеством страниц/элементов и SHA-256 каждого
файла. Готовый каталог появляется атомарным переименованием только после
успешного завершения; оборванный запуск остаётся явно помеченным `.partial`.
Постраничная выборка имеет явную сортировку по возрастанию исходного `ID`.
После чтения определений списка запрос явно выбирает стандартные поля и все
`PROPERTY_*`; состав выбранных полей фиксируется в manifest.
Формат 2 добавляет `users.json`: только ID, активность, ФИО, email и должность,
полученные через `user.get`; телефоны и остальные данные профиля исключаются.

Снимок является чувствительным одноразовым миграционным артефактом. Он хранится
вне Git с правами `0700/0600`, резервируется только в зашифрованном контуре и
удаляется после приёмки по согласованному сроку. Секретный webhook URL никогда
не записывается. Транспорт сохраняет allowlist read-only методов.

Инвентаризация читает только готовый снимок, сначала проверяет его контрольные
суммы и формирует минимизированный отчёт. В отчёт входят статусы, исходные ID,
числовые кандидаты номера и структурные ключи файлов, но не значения
пользовательских полей, имена файлов и URL.

## Последствия

- анализ и будущий маппинг воспроизводимы без повторного доступа к Bitrix24;
- JSONL допускает потоковую обработку и возобновляемые последующие этапы;
- SHA-256 обнаруживает случайное изменение файлов, но не заменяет подпись и
  контроль доступа к каталогу;
- REST-пагинация не даёт транзакционного среза, поэтому на время полного чтения
  изменения источника организационно замораживаются либо проверяются повторным
  снимком;
- реальный снимок нельзя использовать в CI: тесты строятся только на
  синтетических элементах.
- ручная сверка источника подтвердила, что отображаемый архивный номер равен
  `ID` элемента; `ID` используется и для high-water mark диапазона новых заявок.
- файлы из `DETAIL_TEXT` обслуживаются старым OAuth-приложением, а не REST-
  файловым свойством списка; одноразовая выгрузка использует изолированный
  браузерный профиль, строгий allowlist URL и удаляемую после приёмки сессию.
