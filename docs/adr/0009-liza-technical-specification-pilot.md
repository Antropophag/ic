# ADR 0009: пилот анализа ТЗ через ЛИЗУ

Статус: принято

## Контекст

Порталу нужен узкий read-only сценарий параллельного анализа уже приложенного к
заявке ТЗ и формирования черновика ТЗ на испытания. ЛИЗА доступна через
совместимый с Open WebUI HTTP + Socket.IO протокол. Credential и полный текст
документа не должны попадать в браузер или журналы.

## Решение

HTTP-контроллер вызывает два application use case через `LizaPort` и порт чтения
ТЗ. Infrastructure выбирает только актуальные PDF/DOCX с характерным названием,
повторно применяет ACL скачивания документа, читает файл из приватного хранилища
и загружает исходный PDF/DOCX в Open WebUI. Извлечение текста и подготовка файла к анализу
выполняются штатным file pipeline AI-сервера. После completion временная копия удаляется;
сбой удаления сохраняет только внешний file ID в ограниченной по retention retry-очереди.

Анализ и черновик являются независимыми задачами: каждая заново читает и загружает
исходный документ, создаёт собственные `chat_id`, Socket.IO session и локальную
запись conversation с явным типом задачи. Общего mutable conversation state и
зависимости черновика от результата анализа нет. Ответы ничего не меняют в заявке.

AI endpoints используют отдельный idempotency lifecycle: короткие транзакции
reserve/finalize окружают внешний вызов, но не охватывают его. Активные lease
задают per-user/global concurrency limits и освобождаются после конечного
completion timeout. На пользователя одновременно допускается одна задача каждого
типа (analysis и draft), глобальный лимит остаётся общим.

Функция включается только `LIZA_AI_ENABLED=1`. Сейчас backend читает из secret
environment пользовательский JWT Open WebUI; он не входит в DTO и не передаётся
во frontend. Это осознанное ограничение пилота: **NOT FOR PRODUCTION** до замены
JWT на официальный server-to-server API key/service account/service credential
или отдельный API агента ЛИЗЫ, формализации retention и проверки нагрузки.

## Последствия

- недоступность ЛИЗЫ изолирована от основного workflow и возвращает 503;
- поддержка типа файла, OCR и лимиты размера зависят от конфигурации Open WebUI;
- conversation хранит только технические идентификаторы, не prompt и не ответ;
- cleanup queue хранит только внешний file ID, сроки и технический класс ошибки;
- Socket.IO сессия устанавливается напрямую через WebSocket-only transport и
  сохраняет серверный Socket.IO SID, требуемый Open WebUI.
- при появлении стабильного API агента ЛИЗЫ Infrastructure adapter желательно
  перевести с внутренних Open WebUI/Socket.IO механизмов на этот API.
