# ADR 0004: идемпотентность изменяющих HTTP-команд

## Статус

Принято.

## Контекст

Optimistic locking защищал заявки от потерянных обновлений, но не позволял
отличить новую команду от повтора уже успешно завершившегося POST после timeout.
Создание заявки, комментарий и загрузка файла могли породить дубли, а переходы
возвращали ложный конфликт вместо результата первой попытки.

## Решение

Production POST-команды заявок и администрирования требуют `Idempotency-Key`.
Backend связывает SHA-256 ключа с пользователем, методом и фактическим путём,
сравнивает fingerprint JSON либо multipart-файла и выполняет команду вместе с
записью успешного ответа в одной транзакции MariaDB. Конкурентные claim одного
scope сериализуются connection-level lock MariaDB до открытия транзакции;
повтор ждёт завершения первой успешной попытки и получает тот же статус, JSON и
`Location`. После `4xx`, `5xx` или rollback ключ освобождается, поэтому следующая
попытка выполняет команду заново, а не replay-ит ошибку.
Unique index остаётся окончательной защитой и поддерживает смешанный rollout.

Ошибки и rollback не сохраняются. Записи живут 24 часа; истёкший scoped key
атомарно заменяется новой попыткой. Фоновое обслуживание запускается
вероятностно примерно для 1% команд и удаляет по индексу expiry не более 100
строк. Frontend повторно использует ключ незавершённого намерения
после сетевой или серверной ошибки и объединяет одновременные одинаковые вызовы.
Существующие unique constraints и `lock_version` сохраняются.

Auth POST исключены: они управляют сессией, а хранение либо replay ответа входа
создало бы новый credential/session contract. Development seed и CLI import
имеют собственные ограничения; импорт уже идемпотентен по `legacy_id`.

## Последствия

- не нужны Redis, broker или новый runtime-сервис;
- ключ другого пользователя не раскрывает и не воспроизводит его ответ;
- повтор ключа с другим содержимым возвращает `409`;
- SMTP остаётся at-least-once после передачи письма внешнему серверу;
- гарантированный replay ограничен 24 часами.
- старые открытые вкладки после обновления backend получают безопасный `422` и
  требуют reload; fallback без ключа намеренно отсутствует.
