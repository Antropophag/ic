# HTTP API

Базовый префикс: `/api/v1`. Формат запросов и ответов — JSON. Ошибки валидации
возвращают `422`, отсутствие аутентификации — `401`, ошибки workflow — `409`.

## Аутентификация

В production запросы будут использовать серверную сессию, созданную после
LDAP bind. До реализации Identity-модуля заголовок `X-Dev-User-ID` принимается
только при `APP_ENV=dev`; во всех остальных окружениях он игнорируется.

До подключения LDAP фронтенд выбирает актёра переключателем профиля в шапке
среди пользователей, созданных `./yii dev/seed`, и подставляет его в заголовок
на каждый запрос. Выбор сохраняется в `localStorage` браузера. Смена профиля
закрывает открытую карточку заявки и перезагружает реестр, чтобы капабилити
и вкладка «Мои заявки» пересчитались под нового актёра.

`dev/seed` создаёт пять основных ролей (id 1–5: руководитель ИЦ, исполнитель,
сотрудник, эксперт, сотрудник СБ) под фиксированными id, на которые ссылаются
smoke-тесты и E2E, и ещё шесть исполнителей ИЦ по списку ТЗ 7.5 (Наумов,
Прикуль, Шапошников, Галкин, Козлов, Нелидова) — их id не фиксирован и
резолвится по уникальному `ad_login`, чтобы повторный запуск на персистентной
демо-базе не переписал случайно совпавший по номеру реальный профиль.

## Заявки

### `GET /api/v1/executors`

Возвращает только активных пользователей с ролью `Исполнитель ИЦ`. Список
используется серверно управляемой формой назначения.

### `GET /api/v1/requests`

Возвращает последние доступные пользователю заявки:

```json
{
  "items": [
    {
      "id": 1,
      "number": 1,
      "status": "registered",
      "lockVersion": 1,
      "product_name": "Образец продукции",
      "initiator_name": "Иван Иванов"
    }
  ]
}
```

Каждый элемент также содержит текущее назначение, `lock_version`, `color`
(ручная цветовая метка руководителя), `security_mark` (`approve`/`return`/
`null` — решение последнего контроля СБ, если он проводился) и вычисленные
сервером признаки доступных действий, включая `can_security_decide`. Frontend
использует их только для отображения элементов управления; API повторно
проверяет полномочия.

### `GET /api/v1/requests/{id}`

Возвращает карточку заявки и хронологию разрешённых успешных событий. Карточка
доступна любому активному авторизованному сотруднику. Для отсутствующей заявки,
несуществующего или отключённого локального профиля возвращается одинаковый
ответ `404`, не раскрывающий наличие записи.

В `history` входят процессные переходы и успешное назначение исполнителя с
идентификатором правила, автором и временем. Технический `payload_json`,
отклонённые действия и секретные данные аудита через этот endpoint не выдаются.
Для возврата из СБ переход также содержит пользовательскую причину в `reason`.
Поле `comments` содержит комментарии в хронологическом порядке с назначенными
сервером автором и временем. Признак `item.can_comment` сообщает интерфейсу,
доступна ли форма комментария в текущем статусе; сервер в любом случае повторно
проверяет правило при записи. Карточка возвращает не более 50 последних
комментариев. `commentsPage.hasMore` и `commentsPage.nextBeforeId` указывают,
доступны ли более ранние записи.
Поле `documents` содержит только последние версии документов и не раскрывает
физические пути или ключи хранилища. `item.can_upload_document` управляет
видимостью загрузки, но не заменяет серверную проверку.

### `GET /api/v1/requests/{id}/comments?beforeId={id}`

Возвращает до 50 более ранних комментариев перед указанным идентификатором.
Ответ содержит `items`, `hasMore` и следующий `nextBeforeId`; это ограничивает
размер карточки и DOM независимо от общей длины обсуждения.

### `POST /api/v1/requests/{id}/comments`

Добавляет неизменяемый текстовый комментарий:

```json
{"body": "Образцы переданы в испытательный центр."}
```

Пустой текст и текст длиннее 10 000 символов возвращают `422`. Комментарии
разрешены от регистрации до решения СБ включительно; после закрывающего решения
API возвращает `409`. Автор и время берутся только из серверного контекста.
Текст сохраняется в таблице комментариев, но не копируется в технический аудит.

### `POST /api/v1/requests/{id}/documents`

Принимает `multipart/form-data` с полем `file`. Разрешены PDF, PNG, JPEG, DOCX и
XLSX размером от 1 байта до 10 МБ; расширение проверяется вместе с MIME,
определённым по содержимому. Для DOCX и XLSX дополнительно проверяется структура
пакета Office и ограничивается его распакованный размер. Обычный ZIP с подменённым
расширением отклоняется. Повторная загрузка с тем же именем создаёт новую
неизменяемую версию. Успешный ответ `201` содержит метаданные и SHA-256, но не
содержит физический ключ. `409` означает закрытый этап, `422` — недопустимый файл.

### `GET /api/v1/document-versions/{id}/download`

Возвращает байты конкретной версии только активному авторизованному сотруднику.
До завершения заявки отчёт испытаний доступен только назначенному исполнителю и
руководителям ИЦ/лаборатории. Заключение доступно назначенному эксперту, автору
конкретной редакции, руководителям и сотрудникам СБ; посторонний сотрудник
получает тот же `404`, что и для отсутствующей версии.
Файл выдаётся как attachment с исходным безопасным именем; успешное скачивание
попадает в аудит. Отсутствующая версия и отсутствующий физический файл дают
одинаковый `404`.

### `POST /api/v1/requests/{id}/report`

Принимает PDF-отчёт в поле `file` размером до 10 МБ. Загрузка доступна назначенному
исполнителю и руководителям ИЦ/лаборатории для заявки в работе или на подготовке
заключения. Первая версия всегда атомарно увеличивает `lockVersion` и при статусе
`in_progress` переводит заявку в `opinion_preparation`. Это относится и к
импортированной заявке, уже находящейся в `opinion_preparation`. Повторная загрузка
создаёт неизменяемую версию того же отчёта.
Ответ `201` возвращает безопасные метаданные, новый статус и версию блокировки;
`403` означает нарушение DOC-001, `422` — неподходящий файл по DOC-002A.

### `POST /api/v1/requests`

```json
{
  "productName": "Образец продукции",
  "manufacturer": "Производитель",
  "supplier": "Поставщик",
  "sampleQuantity": 1,
  "testMethod": "Типовая программа испытаний"
}
```

Номер назначается транзакционно. Инициатор и время берутся только из серверного
контекста. Успешный ответ имеет статус `201` и заголовок `Location`.
Сотрудник испытательного центра (`Исполнитель ИЦ`, `Руководитель ИЦ`,
`Руководитель лаборатории`) не может подать заявку; попытка возвращает `403`
с правилом `REQ-001` (business-rules.md).

### `POST /api/v1/requests/{id}/executor`

Назначает активного пользователя с ролью `Исполнитель ИЦ`:

```json
{
  "executorId": 42,
  "lockVersion": 1
}
```

Действие доступно руководителю ИЦ и руководителю лаборатории. Успешное и
отклонённое назначения записываются в аудит. Повторное назначение закрывает
предыдущую запись истории и создаёт новую в одной транзакции. Команда принимает
версию из реестра, работает только пока заявка зарегистрирована и увеличивает
`lockVersion`, поэтому устаревшее назначение возвращает `409`.

Ответ `403` содержит идентификатор нарушенного правила `WF-001` или `WF-002`,
`404` означает отсутствие заявки или пользователя, `409` — конкурентное
изменение или смену статуса, `422` — ошибку тела запроса.

### `GET /api/v1/experts`

Возвращает активных пользователей с ролью `Эксперт` для серверно управляемого
списка назначения.

### `POST /api/v1/requests/{id}/expert`

Назначает эксперта на этапе `opinion_preparation`:

```json
{
  "expertId": 42,
  "lockVersion": 4
}
```

Действие доступно руководителю ИЦ или лаборатории. Сервер блокирует заявку,
проверяет актуальную версию, активность и роль эксперта, закрывает прежнее
назначение и создаёт новое в одной транзакции. Успешный ответ содержит новую
`lockVersion`; `403` соответствует правилам `WF-010`, `WF-011` или `DOC-005`,
`409` означает конкурентное изменение, `404` — отсутствие заявки или эксперта.

### `POST /api/v1/requests/{id}/security-decision`

Сохраняет решение активного сотрудника СБ по актуальной редакции заключения:

```json
{"decision": "return", "reason": "Уточнить вывод по испытаниям.", "lockVersion": 6}
```

`approve` завершает заявку, `return` возвращает её в работу и требует причину до
5 000 символов. Решение, переход, аудит и увеличение `lockVersion` выполняются в
одной транзакции; повторное или устаревшее действие отклоняется. `403` означает
неверную роль или этап, `409` — конкурентное изменение, `422` — ошибку тела.

### `POST /api/v1/requests/{id}/start`

Переводит зарегистрированную заявку в работу:

```json
{
  "lockVersion": 1
}
```

Действие доступно активному текущему назначенному исполнителю, активному
руководителю ИЦ и активному руководителю лаборатории. Текущий `lockVersion`
клиент получает в `GET /api/v1/requests`. Сервер под блокировкой заявки повторно
проверяет версию, статус и актуальное назначение, затем увеличивает версию и
записывает переход и событие аудита.

### `POST /api/v1/requests/{id}/reject`

Отказывает в проведении испытаний из статуса `registered` или `in_progress`:

```json
{
  "lockVersion": 1
}
```

Действие доступно активному руководителю ИЦ или лаборатории (`WF-006`).
Инициатор уведомляется по email. `403` означает недостаточную роль, `409` —
конкурентное изменение или неподходящий статус, `422` — ошибку тела запроса.

### `POST /api/v1/requests/{id}/withdraw`

Отзывает заявку из статуса `registered`, `in_progress`, `suspended` или
`opinion_preparation` (до контроля СБ):

```json
{
  "lockVersion": 1
}
```

Действие доступно только активному инициатору заявки (`WF-007`). Назначенный
исполнитель и активные руководители ИЦ/лаборатории уведомляются по email.
`403` означает, что актор не является инициатором, `409` — конкурентное
изменение или неподходящий статус, `422` — ошибку тела запроса.

### `POST /api/v1/requests/{id}/color`

Устанавливает ручную цветовую метку строки заявки (не является статусом,
WF-009):

```json
{
  "color": "red",
  "lockVersion": 1
}
```

Допустимые значения: `white`, `red`, `orange`, `blue`, `violet`, `green`.
Действие доступно только активному руководителю ИЦ или лаборатории и работает
в любом статусе заявки. Событие аудита записывается с правилом `WF-009`;
`403` означает недостаточную роль, `409` — конкурентное изменение, `422` —
недопустимый цвет.

### `POST /api/v1/requests/{id}/opinion`

Публикует текст заключения назначенного эксперта:

```json
{
  "body": "Образец соответствует заявленным требованиям.",
  "lockVersion": 5
}
```

Текст должен содержать от 10 до 20 000 символов. Сервер под блокировкой заявки
повторно проверяет активность и текущее назначение эксперта, формирует PDF с
реквизитами заявки и подписью эксперта, сохраняет неизменяемую версию документа,
переводит заявку в `security_review` и увеличивает `lockVersion`. Документ,
переход и аудит фиксируются одной транзакцией; при откате физический PDF удаляется.
`403` соответствует `AUTH-003`, `DOC-005` или `DOC-007`, `409` означает
устаревшую версию, `422` — ошибку тела запроса.

Успешный ответ содержит `status: "in_progress"` и новую `lockVersion`. Ответ
`403` означает нарушение WF-004 или AUTH-003, `409` — запрещённый переход WF-003 или
конкурентное изменение, `404` — отсутствие заявки, `422` — ошибку тела запроса.

## Диагностика

- `GET /health/live` проверяет только работающий процесс;
- `GET /health/ready` дополнительно проверяет соединение с MariaDB и доступность
  persistent-хранилища документов фактической write/delete-пробой с уникальным
  временным файлом.
