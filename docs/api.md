# HTTP API

## Машиночитаемый контракт

Официальный машиночитаемый контракт хранится в YAML-first спецификации
`openapi/openapi.yaml`. После запуска deployment она доступна по
`/api/openapi.yaml`, Swagger UI — по `/api/docs/`. Проверка выполняется командой
`make openapi-validate` и входит в `make check`; генерация не требуется.

На первом этапе OpenAPI покрывает `GET /health/live`,
`GET /api/v1/auth/me`, `GET /api/v1/requests`,
`GET /api/v1/requests/dashboard` и
`POST /api/v1/requests/{id}/comments`, а также критические действия с заявкой,
административный список пользователей и отзыв роли. Остальные существующие маршруты будут
добавляться постепенно. Отсутствие маршрута в спецификации на этом этапе не
означает, что маршрут отсутствует в приложении.

OpenAPI фиксирует HTTP paths, параметры, тела, схемы ответов, статусы и security
requirements. Этот документ сохраняет контекст бизнес-процессов, детали
идемпотентности, ограничения безопасности и эксплуатационные пояснения.

Swagger UI использует только локальные assets и доступен также в production:
публикуемая спецификация не содержит секретов или внутренних environment
values. `Try it out` отключён, потому что API использует server-side session
cookie и связанный CSRF cookie/header. UI не эмулирует JWT/OAuth и не обходит
реальную защиту. Для практической проверки изменяющих запросов используйте
frontend или integration/E2E тесты.

Изменение публичного API должно сопровождаться соответствующим обновлением
OpenAPI-контракта.

`GET /api/v1/requests/dashboard` возвращает применимые текущему пользователю
категории действий и поле `operational_summary` со счётчиками нагрузки ИЦ,
экспертизы и СБ, а также детализацией направлений. Сводка доступна всем
аутентифицированным пользователям, но состав исполнителей в `directions[].executors`
возвращается только руководителям ИЦ и лабораторий; для остальных ролей массив пуст.
Для каждого доступного исполнителя поля `in_progress` и `suspended` раздельно
показывают число заявок в работе и приостановленных заявок. Поле направления
`unassigned` содержит заявки без текущего исполнителя.
Operational summary вычисляется для общей текущей нагрузки портала, а персональные
категории `categories` — для scope текущего пользователя; обе части не зависят от
параметров реестра. Параметр `status` в `GET /api/v1/requests` принимает один или несколько
статусов через запятую без пробелов и пустых элементов; отсутствие параметра или
пустая строка не ограничивают выборку по статусу. Дубликаты удаляются с сохранением
порядка первого появления, но исходный список не может содержать более восьми элементов.
`attention` принимает только идентификатор из
этого набора и сужает обычную серверную выборку; подмена идентификатора не даёт
прав, а неизвестное значение возвращает `422`. Read-only dashboard использует
обычную session cookie и не требует CSRF либо `Idempotency-Key`.

Все публичные маршруты доступны через сервис `frontend` под `/api/v1`.
`GET /api/v1/auth/me` возвращает CSRF token и текущего пользователя:

```json
{"csrfToken":"...","user":null}
```

Обычная авторизация использует `POST /api/v1/auth/login` с LDAP login/password
и серверную session cookie. Тот же endpoint принимает заранее настроенный
break-glass логин, но локальная проверка выполняется только при точном совпадении
логина. Неверный пароль для совпавшего логина возвращает тот же общий `401`
`Неверный логин или пароль`, что и отклонённая LDAP-аутентификация, без
специального признака аварийной identity. Все остальные логины всегда передаются
LDAP. Если каталог недоступен, endpoint возвращает `503`, а интерфейс предлагает
обратиться в техническую поддержку. Успешный локальный вход создаёт ту же session
cookie, что LDAP-вход.

POST-маршруты, принимающие DTO в JSON, требуют непустое тело в формате JSON
object с `Content-Type: application/json` (параметр `charset` допускается):

- отсутствующий или другой `Content-Type` возвращает `415`;
- пустое или некорректное JSON-тело возвращает `400`;
- JSON array, scalar и `null` возвращают `400`;
- `{}` проходит разбор JSON object и передаётся в DTO validation;
- корректный JSON object, не прошедший валидацию DTO, сохраняет прежний ответ
  `422` в формате `{"errors": {...}}`.

Маршруты без DTO body, включая logout, этого тела не требуют. Отзыв роли
принимает JSON object с обязательным полем `reason`.
Загрузка документов и отчётов использует `multipart/form-data`.

Черновик акта испытаний представлен ресурсом
`/api/v1/requests/{id}/report-document-drafts/test-act`: `GET` возвращает
актуальные автозаполненные поля, `POST` принимает уточнённые реквизиты и возвращает
DOCX. Операция доступна назначенному исполнителю и руководителю ИЦ/лаборатории в
состояниях `Заявка в работе` и `Подготовка заключения`, а также в состоянии
`Заявка выполнена`, если после удаления отсутствует действующий отчёт. Операция
не сохраняет файл и не изменяет заявку.

Критические действия — операции, которые отклоняют или отзывают заявку,
приостанавливают её обработку, возвращают её на доработку, удаляют результат
работы либо отзывают полномочие пользователя. Команды `reject`, `withdraw`,
`suspend`, возврат с контроля СБ,
удаление отчёта и отзыв роли требуют строку `reason`: после обрезки пробелов она
должна содержать от 1 до 5000 символов. Отсутствующее, пустое или состоящее
только из пробелов значение возвращает `422`; изменение данных без причины не
выполняется.

Согласование службой безопасности (`decision=approve`) не принимает причину:
непустой `reason` возвращает `422`. Отсутствующее, `null` или пустое после
обрезки значение допустимо и не сохраняется в аудите. Если для решения нет
актуального непроверенного экспертного заключения, endpoint возвращает `409`
без изменения заявки, success audit и notification outbox.

## Идемпотентность изменяющих команд

Все production `POST` маршруты заявок и администрирования требуют заголовок
`Idempotency-Key`: 16–128 символов из `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, `-`,
первый символ буквенно-цифровой. Обычно клиент передаёт UUID v4.

- первый успешный запрос возвращает обычный `2xx` и
  `Idempotency-Replayed: false`;
- повтор с тем же пользователем, методом, фактическим route path, ключом и содержимым возвращает
  исходные status, JSON и `Location` с `Idempotency-Replayed: true`;
- тот же ключ с другим JSON или файлом возвращает `409`;
- полностью одновременный повтор ждёт первую попытку не более 30 секунд; при
  превышении этого времени возвращается безопасный `409` без выполнения action;
- отсутствующий/некорректный ключ возвращает `422`;
- `4xx`, `5xx` и транзакционный rollback не запоминаются: исправленный запрос
  или retry с тем же ключом выполняется заново;
- replay гарантирован 24 часа после первой успешной попытки.

JSON fingerprint строится из canonical JSON: порядок ключей объектов и пробелы
не имеют значения, порядок элементов массивов сохраняется. Некорректный JSON
хешируется как raw body и затем отклоняется обычной валидацией. Multipart
fingerprint включает canonical form fields и каждый файл: имя поля, клиентские
метаданные и streaming SHA-256 фактического содержимого. Порядок multipart
parts, boundary и порядок нескольких файлов не меняют fingerprint; содержимое
файла целиком в память не загружается.

Scope включает actor, HTTP method и нормализованный Yii `pathInfo` с resource
ID. Query string намеренно исключён: изменяющие маршруты не принимают команды в
query parameters. `pathInfo` не содержит ведущий slash и уже декодирован Yii;
route table принимает только объявленную форму пути, поэтому альтернативный
trailing slash не доходит до action. Reverse proxy передаёт `/api` без
переписывания resource path.

Из ответа сохраняются только status, JSON body размером не более 65 535 байт и
`Location` размером не более 2 048 байт. `Set-Cookie`, CSRF, tracing,
hop-by-hop, debug, Nginx и прочие headers никогда не сохраняются и не
replay-ятся. Поддерживаются JSON object/array/scalar/null, пустой результат и
`204`; replay `201` восстанавливает `Location`, но не запускает action повторно.

Старый открытый frontend bundle не умеет сформировать ключ. После обновления
backend такой POST безопасно отклоняется с `422` до выполнения команды; тихого
неидемпотентного fallback нет. Пользователь должен перезагрузить вкладку.
Deployment выполняется штатным `make prod-up`, который собирает обе части; для
длительно открытых вкладок следует заранее объявить обязательную перезагрузку.

Ключ scoped текущим серверно аутентифицированным пользователем и хранится только
как SHA-256. `POST /auth/login`, `POST /auth/logout` и development seed не входят
в этот контракт. `lockVersion` остаётся обязательным для защиты разных команд,
конкурирующих за одну заявку.

Development deployment дополнительно монтирует маршруты:

- `GET /api/v1/dev/users` — безопасный список активных seeded users;
- `POST /api/v1/dev/seed-requests` — подготовка development-данных; запрос
  требует выбранного активного пользователя с ролью `administrator`, удаляет
  прежние данные заявок и создаёт 100 синтетических заявок на всех стадиях.
  Набор включает обсуждения разной длины, сопроводительные документы в форматах
  PDF, PNG, JPG, JPEG, DOCX и XLSX, а также PDF-отчёты и PDF-заключения. Успешный
  ответ содержит счётчики `requests`, `comments` и `documents`.

Они отсутствуют в production и test route table. Header `X-Dev-User-ID`
принимается только когда `compose.dev.yaml` смонтировал development
конфигурацию. Аналогично `X-Test-User-ID` физически подключается только
`compose.test.yaml` и не является частью production-конфигурации.

Бизнес-маршруты заявок используют idempotency key и optimistic lock version и возвращают
структурированные JSON ошибки. Полный контракт закреплён Integration и
Playwright тестами.

`POST /api/v1/requests` не принимает подразделение от клиента. Backend берёт
его из текущего профиля; если оно отсутствует, возвращается `422` с понятной
бизнес-ошибкой. Список и карточка возвращают историческое поле `department`;
для legacy-заявки без снимка это строка `Подразделение не указано`.
Технические `department_source` и `department_external_id` в пользовательский
контракт не входят.

`POST /api/v1/requests/{id}/department` принимает `department` и
`lockVersion`. Маршрут доступен только активному администратору, очищает
внешний ID снимка и возвращает `403`, `404`, `409` или `422` по общим правилам.
Карточка содержит вычисленный backend-флаг `can_edit_department`.

## Read-only журналы администратора

Только активный пользователь с ролью `administrator` может читать журналы.
Оба ответа имеют форму `{items, hasMore, nextCursor}`, сортируются по
`createdAt DESC, id DESC` и используют непрозрачный `cursor`; `limit` по
умолчанию 50 и не может превышать 100.

`GET /api/v1/admin/audit-events` принимает `actorId`, `eventType`,
`entityType`, `entityId`, `requestId`, `result=all|denied`,
`dateFrom`, `dateTo`, `limit`, `cursor`. Даты имеют формат `YYYY-MM-DD`.
Элемент содержит raw `eventType`, title, actor, entity, ruleId, result и
whitelist `details`. Полный `payload_json` не выдаётся. Причины, тексты,
токены и внутренние данные исключены; неизвестный тип становится безопасным
«Системным событием» без details.

`GET /api/v1/admin/notifications` принимает `status`, `requestId`,
`eventType`, `recipient`, `dateFrom`, `dateTo`, `problematic=1`, `limit`,
`cursor`. Допустимые статусы: `pending`, `sending`, `sent`, `failed`.
`health` равен `failed` для окончательной ошибки, `stale` для `sending` с
истёкшим lease либо `pending`, просроченного более чем на 300 секунд (текущий
размер lease worker), `retrying` при более чем одной попытке, иначе `normal`.
Поле `body` не выбирается. Raw `last_error` не раскрывается: API возвращает
нейтральное «Ошибка SMTP».

## Активность пользователей для администратора

`GET /api/v1/admin/users` доступен только активному администратору и расширяет
существующее представление пользователя nullable-полями `lastLoginAt` и
`lastActivityAt`. Оба значения имеют UTC ISO 8601; для ещё не входившего или не
проявлявшего активности пользователя возвращается `null`. `checkedAt` содержит
серверное время формирования ответа, чтобы frontend не зависел от расхождения
часов при определении недавней активности.

`lastLoginAt` меняется только после успешной LDAP или break-glass
аутентификации. `lastActivityAt` обновляется best-effort при authenticated API
request не чаще раза в пять минут. Health probes, статические файлы и запросы
без действующей identity это состояние не меняют. Эти timestamps являются
операционным состоянием, а не историей действий и не заменяют audit log.
Frontend показывает «Активен» для activity не старше десяти минут: запас в один
throttle-интервал не даёт непрерывно работающему пользователю мигать между
состояниями на границе очередного разрешённого обновления.

## AI-пилот обработки технического задания

`POST /api/v1/requests/{id}/ai/technical-specification/analyze` и
`POST /api/v1/requests/{id}/ai/technical-specification/draft` — независимые
PILOT endpoints анализа ТЗ и формирования черновика ТЗ на испытания. Оба требуют
session/CSRF и отдельный `Idempotency-Key`; необязательный `documentVersionId`
выбирает доступную актуальную PDF/DOCX-версию. Ответ `200` является discriminated
union по `status`: `completed`, `choice_required` или `not_found`.

Для AI используется специализированный reserve → внешний вызов вне DB transaction
→ finalize lifecycle. `Idempotency-Replayed` показывает replay сохранённого
ответа; `409` означает конфликт key, уже выполняющуюся операцию или исчерпанную
AI concurrency capacity. `422` означает некорректную/недоступную версию, `503` —
выключенную функцию, timeout, malformed AI response или недоступность ЛИЗЫ.
Внутренние Open WebUI endpoints не являются публичным API портала. Полные
эксплуатационные семантики приведены в [руководстве интеграции](integrations/liza.md).

## Состояние системы для администратора

`GET /api/v1/admin/system-overview` доступен только активному администратору и
не заменяет `/health/ready`. БД, LDAP, SMTP и файловое хранилище проверяются
независимо; ошибки не раскрывают исключения и credentials. Ответ содержит
безопасную фактическую конфигурацию: имя и версию БД, LDAP endpoint/domain/Base
DN/TLS, SMTP endpoint/TLS/отправителя, путь и свободное место хранилища. LDAP
probe проверяет TCP endpoint и, когда включён `LDAP_USE_TLS`, StartTLS handshake,
но не выполняет bind без пользовательского пароля. Ключи `details` являются
стабильными англоязычными API identifiers; русские подписи формирует frontend.
Отсутствующая конфигурация переводит только соответствующую зависимость в
`error`, не прерывая остальные probes.
